# E076 — global cap for Jev card-selection candidates

Issue: [#144](https://github.com/yzxoi/RSI-Jev-Slay-the-Spire-2/issues/144). Baseline: merged `origin/main` `0ab503b2a225d2aac1c031d4d13bff4a4b9d5253`. E075 Silent A0 `e075_weak_003` stopped at an optional Act 2 floor 1 card selection after Jev returned HTTP 400. The exact source trace SHA-256 was `336b20373e64fac10fde04cd6bf021be345b455c2a003d9908b853f42ae8fb26`. Its final request had 249 candidates and 82,776 JSON bytes. Candidate generation caps each combination-size batch, so its total can exceed the intended 128. The provider did not return a detailed 400 reason; the oversized request is a hypothesis, not a proven cause.

Freeze the [model context](frozen-card-select.json) from source request sequence 1296 before implementation; it retains the same scene and prior-decision context, original request hash, candidate count and byte count without credentials. Compare baseline `macro_candidates` with a treatment that caps the entire list at 128 while reserving `skip_select` when legal. This experiment sends one live Jev request per version from the frozen context but **does not send a game action**. Pinned model `typesafe/jev-1.13-20260917`, game v0.111.0 and sts2-cli `084d1aa3d8e118ca7ce8d8774ad16d6be9c92367` are unchanged. Raw requests/responses, accepted candidate choice, usage and hashes remain under ignored `artifacts/runs/`; publish compact results here.

Decision: baseline must reproduce HTTP 400 on 249 candidates. Treatment must present no more than 128 legal candidates including skip, obtain one valid model choice, pass repository tests, and leave non-card-selection policies untouched. Merge only then. If baseline does not reproduce, close as inconclusive rather than claiming the cap caused the previous error. This is model-call compatibility, not battle strength or a win-rate result.

## Iteration 2 — global candidate cap

Implementation and regression tests were committed as `ff08bc7002f37575cb818999d86b1df023b2e0fe` before evaluation. The code limits the **whole** `card_select` candidate list to 128, reserving one slot for `skip_select` when `min_select == 0`; other decision types are untouched. Commands: `python3 -m unittest discover -s tests -q` (114 passed), then `python3 -m scripts.probe_cardselect_e076 --phase treatment`. From the same frozen context, the generator offered 128 legal candidates including skip, and the request shrank to 45,987 bytes. Jev returned valid choice `a127` (`skip_select`) using pinned model `typesafe/jev-1.13-20260917`; the provider reported $0.000921438 for one call. Raw trace: ignored `artifacts/runs/e076-0b8fabca-4d39-4672-b7b6-d56d826fcd21/decisions.jsonl`, SHA-256 `866257f060591d3b18b65b582bffc317a53bae58d32c4115b6a4d6b2447f4af1`. Compact metadata is in [treatment-result.json](treatment-result.json).

The predeclared compatibility criterion passed. This establishes that the original frozen 249-choice request fails while the capped 128-choice request succeeds; it does not identify whether the provider's limit was candidate count, request bytes or another coupled property. Truncation preserves low-cardinality combinations first, so it also narrows the policy's choice set; any strategy or win-rate effect requires a separate experiment. No game action was issued in either probe.
